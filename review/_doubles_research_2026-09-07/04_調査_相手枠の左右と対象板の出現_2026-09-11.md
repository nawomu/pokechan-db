## #107: ダブルバトルで、相手の選出1番目(相手の枠0)は自分から見て左右どちらに出るか

#### 副産物: 日本Wikiにあった「処理順」の記述(左右の話ではあるが#107の答えではない)
> 「複数を対象とする技のダメージは、第三世代では1P側の1匹目→2P側の1匹目→1P側の2匹目→2P側の2匹の順に、第四世代では[すばやさ]が高いポケモンから処理される。第五世代からは味方→敵から見て左側の敵→右側の敵の順に処理される。」

注意点: これは**技のダメージ処理順**(誰から計算するか)の話であり、「相手の選出1番目がどちらに立つか」とは別の情報。「敵から見て左側」という言い回しは「敵自身の視点での左」を指しており、後述のはてなブログの「向かって右→向かって左」(=攻撃側の画面上の右→左)と向きが一致する(敵の左=攻撃側から見て右、なので整合)。**#107には使えないが、盤面の左右概念そのものは第五世代から公式に存在することの裏付けにはなる**。

#### Pokémon Showdownクライアント実装(B・非公式ファンサイトだが公式仕様のシミュレーションとして広く使われる実装)
出典: `https://github.com/smogon/pokemon-showdown-client`
- `play.pokemonshowdown.com/src/battle.ts`(Sideクラス):
```
this.isFar = !!(n % 2);
...
leftof(offset: number) {
    return (!this.isFar ? -1 : 1) * offset;
}
```
  (`n`はp1=0,p2=1,p3=2,p4=3。自分視点で近い側=p1系列は`isFar=false`、相手側=p2系列は`isFar=true`)
- `addPokemonSprite`(`battle-animations.ts`)で、各ポケモンのスプライトは `pokemon.side.isFar` を`isFrontSprite`として渡す。`pokemon.slot`はプロトコルの位置(p1a/p1b等のa/b)がそのまま入る(`battle.ts`の`this.active[slot] = pokemon; pokemon.slot = slot;`)。
- 画面上のx座標を決める`recalculatePos(slot)`(`battle-animations.ts`、アクティブ数2体=ダブル戦のケース):
```
case 1:
    if (this.sp.pixelated) {
        this.x = (slot * -100 + 18) * (this.isFrontSprite ? 1 : -1);
    } else {
        this.x = (slot * -75 + 18) * (this.isFrontSprite ? 1 : -1);
    }
    break;
```
  計算すると:
  - 自分側(isFrontSprite=false・isFar=false): slot0(=a、選出1番目) → x = (18)×(-1) = **-18(画面左寄り)**。slot1(=b、選出2番目) → x = (-82)×(-1) = **+82(画面右寄り)**。
    → **自分の選出1番目=左、2番目=右**。これは既に実機観察済みの内容と一致。
  - 相手側(isFrontSprite=true・isFar=true): slot0(=a、相手の選出1番目) → x = 18×1 = **+18(画面右寄り)**。slot1(=b、相手の選出2番目) → x = -82×1 = **-82(画面左寄り)**。
    → **相手の選出1番目=自分から見て右、2番目=左**(自分側と鏡写しの関係)。

注意点(重要):
1. これは**Pokémon Showdownという非公式ファン実装のクライアント描画コード**であり、Nintendo Switch版(SV/剣盾/Champions)の公式UIそのものではない。ただし対戦ロジック(スロットa/bの概念、送り出し順)は公式ルールに準拠して作られている実装であり、「B=他作品(実装)」の参考証拠として提示する。
2. Showdownの`slot`(a/b)は「チーム編成順(選出1番目/2番目)」と厳密に1対1で対応するとは限らない(交代・入れ替えで`slot`は変わりうる)。ただし**戦闘開始時の初期リード出し**に限れば、選出順1番目・2番目がそのままslot0・slot1として送り出される設計になっている。
3. 余談: `battle.ts`には `this.dex = Dex.mod('champions' as ID);` という記述があり(3531行目)、Showdownクライアントには元々「champions」という MOD 名が存在する。ただし本調査で見た範囲では、これは既存のNintendo公式「Pokémon Champions」アプリの再現ではなく、Showdown独自の何らかのフォーマット名の可能性が高く、**#107の直接の根拠としては使わない**(用途不明のため参考情報として記載するのみ)。
4. 実機(03ファイル)のスクリーンショットでは「相手の選出順が見えない」ため、Showdownの推定と実機を直接照合できていない。**Champions実機での最終確認はまだ未了(A区分の確定は要追加観察)**。

## #111: 対象を選ばない技(相手全体・自分以外全体・味方全体・自分・場)や候補が1つしか無い時に「対象選択の画面」が出るか

### 結論: **C(Wiki/Bulbapedia/Serebii/公式/Game8・GameWithに直接の記述なし)。Pokémon Showdownクライアント実装(B)では、技の`target`種別だけで対象選択screenの要否が決まり、「相手全体」「自分以外全体」「味方全体」「自分」「場」に相当する種別では対象選択screenを出さない設計になっている(候補数=1でも同様に出ない、逆に候補が1体しかいない状況で「1体選択」技を使っても、種別が選択可能種別である限り画面は出る=候補数では判定していない)**。

#### Pokémon Showdownクライアント実装(B)
出典: `https://github.com/smogon/pokemon-showdown-client`、`play.pokemonshowdown.com/src/battle-choices.ts`
```
if (choice.choiceType === 'move') {
    const targetable = (this.request as BattleMoveRequest).targetable;
    if (!choice.targetLoc && targetable) {
        const choosableTargets: unknown[] = ['normal', 'any', 'adjacentAlly', 'adjacentAllyOrSelf', 'adjacentFoe'];
        if (choosableTargets.includes(this.currentMove(choice)?.target)) {
            this.current = choice;
            return null;
        }
    }
    ...
```
同ファイル674行目:
```
request.targetable ||= battle.mySide.active.length > 1;
```
読み解き:
- 対象選択screen(`targetLoc`待ち)が要求されるのは、技の`target`種別が `normal`(通常1体)・`any`(任意の1体)・`adjacentAlly`(隣の味方1体)・`adjacentAllyOrSelf`(隣の味方か自分)・`adjacentFoe`(隣の相手1体)のいずれかの場合**だけ**。
- `allAdjacentFoes`(相手全体に相当)・`allAdjacent`(自分以外全体に相当)・`all`(場全体)・`self`(自分)・`allySide`/`foeSide`(自分の場/相手の場)・`allyTeam`・`randomNormal`等は、この`choosableTargets`リストに含まれないため、**技を選んだ時点で即座に確定し、対象選択画面(targetLoc待ち)は出ない**。
- この判定は**技の種別だけ**を見ており、「今場に何体残っているか(候補数)」は一切見ていない。つまり:
  - 「相手全体」等の技は、相手が何体残っていようと画面は出ない(候補が1つでも0でも関係ない=種別で決まる)。
  - 逆に「1体選択」技(normal等)は、たとえ相手の候補が実質1体しかいない状況でも、`targetable`(=自分の場がダブル以上)である限り対象選択画面は出る設計になっている(Showdownの実装では**候補数による自動スキップは行っていない**)。
- `targetable`自体は「自分の場のアクティブ数が2以上か」(=シングルかダブル以上か)だけで決まり、相手の残数とは無関係。

注意点:
1. これはShowdown側の**UI実装**の話であり、Nintendo Switch版本編/Championsの内部仕様を保証するものではない。ただし「技のtarget種別だけで選択要否が決まり、残数では決まらない」という設計思想は、複数の権威ソース(Bulbapedia「Damage」節の"only if there is more than one such target when the move is executed"という一文=**ダメージ倍率の判定は実行時の残数を見る一方で、対象選択の可否自体は技の種別で固定されている**、という棲み分け)とも整合的。
2. 本プロジェクトの既存資料(`03_実機画面の観察_選出と対象選択_2026-09-11.md` 台帳#111)では「SVでは対象が1つでも板が出ない技(味方全体/相手全体)は板を出さない」という実機観察に基づく記述があるが、これは**技の種別による「そもそも選ばせない」ケース**の話であり、今回追加調査した「1体選択技で候補が実質1体しかいない場合」のケースの実機確認はまだ無い(引き続き未確認)。

## おまけ(#110): 対象選択画面のカーソル初期位置の規則

### 結論: **B(SV・非公式だが具体的な観測記録あり)。「対象を選ぶ技の初期位置は、選ぶ側の画面で見て左側」という明記された記述をブログで発見**。Champions実機での確認はまだ無い(A区分は未達成)。

出典: くぼーん(cubone104105)氏のブログ「ダブルバトルの左右で影響の出ることまとめ【左右差あり】」
URL: `https://cubone104105.hatenablog.com/entry/2026/04/06/122130`(2026-04-06付、SV基準の記録。PJCS予選参加等の実績を持つ競技プレイヤーによる記事)

引用(一字一句):
> 「ポケモンチャンピオンズでは無くなっている要素もあるかもしれませんが、一応SVではこういう事例があったという記録です。」

> 「押しミスしてほしい方のポケモンは初手に右側に配置すべき
> 対象を選ぶ技の初期位置は(相手から見て)左側なので、誤ってそのまま押してしまう可能性があります。
> 特に効果的に活かせるのが寿司で、ヘイラッシャが左側でシャリタツが右側になるように置くと合体のターンに攻撃を透かせる可能性が上がります。大きいヘイラッシャが左側なので、見やすさとも噛み合っています。」

> 「ダブルバトルをよくやっているんですが、シングルバトルと違って左（1番目）にも右（2番目）にもポケモンを配置します。」

読み解き:
- 「押しミスしてほしい方を右側に配置すべき」というアドバイスの前提として、「相手が対象を選ぶ画面を開いた時、初期カーソルは(その選ぶ側=相手の画面で見て)左側の候補に乗る」ことが明言されている。つまり**カーソル初期位置は、技を選んだ攻撃側の画面上の“左”に固定されている**という主張であり、「攻撃者自身の位置(正面/同じ側)に連動する」という説とは異なる可能性を示唆する(この記事の書きぶりでは、攻撃者がどちらの枠にいるかに関係なく常に画面左がデフォルトになる、という含意)。
- 同ブログはSV基準であることを明記しており、Championsでの検証はしていない(執筆者自身が「無くなっている要素もあるかもしれません」と留保)。
- また、この記事は「シングルバトルと違って左(1番目)にも右(2番目)にも配置する」と明言しており、**自分の選出1番目=左、2番目=右**という既存の実機観察(03ファイル)と一致する追加の傍証になる。

既存の実機スクリーンショット(`03_実機画面の観察_選出と対象選択_2026-09-11.md`)の観察:
> 「カーソルの初期位置=オオニューラ(上段左)=使用者フラエッテ(自分の左枠)の同じ側」

この実機観察1枚だけでは、「常に画面左がデフォルト」なのか「使用者と同じ側がデフォルト」なのかを区別できない(使用者フラエッテがたまたま自分の左枠だったため、両仮説が同じ結果を予測する)。今回発見したブログの記述は「常に画面左」寄りの主張だが、**Champions実機での複数パターン(使用者が右枠の場合も含む)の追加確認が必要**。台帳#110は依然「未確定」のまま。

## 3行要約

- **#107(相手の選出1番目の左右)**: Wiki/Bulbapedia/Serebii/公式/Game8・GameWithには直接の記述なし(C)。Pokémon Showdownのクライアント描画コード(`battle-animations.ts`の`recalculatePos`・`isFrontSprite`)からは「自分の選出1番目=画面左、相手の選出1番目=画面右」という鏡写しの設計が読み取れる(B・Champions実機では相手選出順が見えず未確認)。
