バトル1ターン Phase全体表 — 特性・持ち物・技効果を「発火フェーズ」で束ねる設計フレーム

作成: 2026-07-23 JST / 対象: real_battle_simulator.html(現エンジン) / 元ネタ: CEDEC 2026 ゲーフリ講演(Section→Event→EventHandler) × 阿部さん正典フェーズ順 × 設計監査(HANDOFF_SESSION_2026_07_23.md)

この文書は何か

ポケモンバトル1ターンを、上から下へ時系列で「フェーズ」に分割し、各フェーズで今どの特性/持ち物/技効果が発火しているかを棚卸しした一覧表。 CEDEC 2026 でゲーフリが公開した設計思想「Section(機能単位) → Event(名前つき介入点) → EventHandler(個別仕様)」を、 このエンジンのデータに当てはめる第一歩として作成する。

技(わざ)の battle_data.effects[].phase は既に on_use / lasting / this_turn / delayed / turn_end の5値を持つが、 これは「フェーズが5種類しかない」という意味ではなく、粗すぎて実際のsim内部フェーズ(優先度判定〜攻撃前〜攻撃〜攻撃後〜ターン終了の十数段)を表現しきれていないという現状を表す。 さらに特性(ABILITY_DESC 全件)・持ち物には phase キーという概念自体が無く、全てエンジン(real_battle_simulator.html)内の if (sideAbility(x)==='◯◯') という特例分岐で発火している(58箇所以上、監査B参照)。

完成条件: 全ての特性・持ち物・技効果が、下表のような「どのフェーズで発火するか」というキーで機械的に分類できるようになったら、エンジンの runTurn() はフェーズを順に流すだけのディスパッチャになり、新しい特性/持ち物を足すたびにコードの複数箇所を手編集する現状(監査Dで指摘した再発バグの根本原因)が構造的に無くなる。

この文書の位置づけ = 第1段(フレーム)。行=フェーズの叩き台と、各フェーズの代表例+分類ルールまで。第2段(全数割り当て) = 全特性(約170)・全持ち物(約100)・全技effects(490+445)を実際にこのフェーズキーへ1件ずつ割り振る作業は、このフレームが確定してから別作業とする。

根拠の付け方: 本文中の記述はすべて ファイル名:行番号 を実コード確認の上で付す。裏取りできていない/コードが実装として存在しない箇所は「未確認」「未実装」と明記し、理想像(阿部さんの正典)とコードの実態を混同しない。
介入点(Event) = 複数のHandlerが相乗りする合流点 gap = 理想フレームと現実装の食い違い・未実装 相対的にうまく合流できている実装(参考)

フェーズ表の読み方

  • # = 上から下へ時系列。同じ番号台は同時に決着する処理群。
  • phaseキー名(案) = 新しい細粒度語彙の候補。これは案であり阿部さんが直す前提(英字keyは他の場所で再利用しやすいよう仮に置いた名前)。
  • ここで発火する機構 = 代表例＋分類ルール(全数列挙ではない=第2段の仕事)。判断が難しい/正典的に重要な機構は必ず具体的に列挙(いかく・まけんき・ミラーアーマー・あまのじゃく・てんねん・もうか・リフレクター・さめはだ/ゴツメ/せいでんき/どくしゅ/ミイラ・じゃくてんほけん/だっしゅつパック/きのみ・天候メイカー・いたずらごころ・どくびし 等)。
  • 介入点(Event)か = そのフェーズが「反応(Handler)が相乗りする合流点」かどうか。◎/○=はい(CEDECのEvent相当)、△=部分的(合流点はあるがHandler登録制でなくif/elseベタ書き、または合流点が複数に分裂)、✗=いいえ(単発計算・Handlerの相乗りなし)。
  • 現エンジンの実装箇所 = 今その処理をやっている関数と行番号(2026-07-23時点の real_battle_simulator.html)。
  • 現状phaseキー対応 = 技effectsの5値(on_use/lasting/this_turn/delayed/turn_end)がこの細かいフェーズのどこに相当するか。特性・持ち物にはそもそもこの5値すら無いので「該当なし(gap)」と明記する。

増分リファクタの最初の一歩

監査Eの結論どおり、applyRankStageGuarded()(real_battle_simulator.html:3467-3541)を本物の名前つきEvent+Handlerリスト化するのが最小リスクの第一歩。 理由: ①既に単一funnel(能力ランク低下は必ずここを通る) ②反応ロジック(あまのじゃく/ミラーアーマー/クリアボディ/かちき・まけんき/ものまねハーブ)が1関数に集約済み ③コード自身のコメント(3455-3457行)が「H2/H3/H4で共有パイプ化した」と経緯を記録している=すでに1回リファクタされた実績がある。 onStatStageChange のような {name, cond, apply} 配列へ抽象化しても、解決順序とログ文言を維持すれば sim825/0・hard174/0 のテスト緑を壊さずに改修パターンを実証できる(次の対象=calcDamageの58特性if分岐、phaseDealDamageの接触反応ブロック)。
